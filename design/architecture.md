This records how the product is built: its stages, engines, models, toolchain and layout. The public interface (CLI, transcript JSON, results file) is in [`public-api.md`](public-api.md). What each choice is judged by is in [`../spec/acceptance.md`](../spec/acceptance.md), G1 to G4. The Owner approves every change to this file. Internal designs, one per phase, go in `design/internal/`.

## Pipeline

```
input file ─► decode ─► audio (16 kHz mono float32)
                          ├─► ASR ──────────► words (text, start, end, probability)
                          └─► diarization ──► speaker turns (start, end, speaker)
                                               │
                    words + turns ─► alignment ─► transcript (speakers, segments, words)
                                                    └─► export: txt, srt, vtt, json
```

- **Decode** (`audio`): PyAV opens the input, which can be WAV, FLAC, MP3, M4A/AAC, or the first audio track of an MP4/MOV. It resamples to 16 kHz mono float32 in memory. This is the only stage that parses untrusted bytes (Q4, Q9). Every failure here becomes an input error (exit 3), and audio with no speech becomes "no speech found" (exit 4).
- **ASR** (`engines`): the engine the user chose (F11), Kyutai STT 1B by default or Apple's recognizer, behind one interface ("Speech engines (G4)"). Both give English words with times (F9). Whisper, and the Silero VAD that came with it, are retired (#565).
- **Diarization** (`diarize`): `pyannote/speaker-diarization-3.1` on pyannote.audio 3.x, run locally, with no speaker count unless the user gives one (F2). It yields speaker turns, which may overlap.
- **Alignment** (`align`): with diarization turns, each turn that holds words is a segment, with the turn's span and speaker (#372). A word goes to the turn holding its midpoint, the one overlapping it most if several do. A word in no turn joins the nearest turn, which stretches to cover it. A turn with no words is left out, and a turn over 30 s splits at word boundaries. Without turns (`--no-diarize`), segments are runs of consecutive words, breaking at a pause of 1 s or more, at the end of a sentence and at 30 s. These words-first rules are also live mode's join: there, each word goes to the speaker whose turn overlaps it most, else the nearest turn within 1 s, else the previous word's speaker, and segments are runs of words with the same speaker, with the same breaks. Speakers are numbered by first appearance, `S1`, `S2`, … (shown as "Speaker 1", …). The internal design fixes the details.
- **Export** (`export`): writes the transcript as plain text, SRT, WebVTT and JSON (F3). All four are rendered from the same in-memory transcript, so they can't disagree.
- **Run order:** ASR and diarization both read the decoded audio and are independent. They run concurrently, in two threads: both spend their time in native code that releases the GIL. So the wall-clock time is roughly the slower of the two. If memory (Q3) or determinism (Q7) needs it, the internal design may run them one after the other.
- **Device:** Kyutai runs on the GPU through MLX, and Apple's engine on the Neural Engine, in macOS's own process. Diarization stays on the CPU, so it doesn't compete with Kyutai for the GPU.

*The options below are G1's (#81), kept as the record; G4 replaced the ASR engine (#565).*

**Options considered (#81, question 6):**
- **A. ASR and diarization side by side, joined at the word level** (above). *Recommended.* It is simple, it runs in parallel, ASR gets whole-file context (better WER), and G2 can reuse every stage.
- **B. Diarize first, then transcribe each speaker turn.** Overlapping speech gets cleaner boundaries, but there are hundreds of short ASR calls with little context: worse WER, and slower.
- **C. WhisperX.** It adds wav2vec2 forced alignment for sharper word times, at the cost of a large, separately pinned dependency tree and less control over determinism. The word times faster-whisper gives are enough for the alignment rules above.

Q3 counts each model separately, at 2.5 GB (#565): Kyutai's ≈ 2.2 GB and the diarization models' ≈ 35 MB each fit. One Kyutai model serves batch and live mode, so the manifest has one ASR default, with no separate live default.

- **Kyutai, as published.** The manifest pins the published bf16 files, and the engine quantizes the language model to 8 bits as it loads them, as `moshi-mlx` does for its `--quantized 8`. The spike measured 8-bit at a WER of 17.3 % on AMI-ci, against 18.3 % for bf16, at 0.44 of real time against 0.54–0.64, with the same delay (#565). Quantizing at load saves no disk, but it needs no converted file of our own to publish under CC BY. The quantization is the same at every load, so it doesn't break Q7.
- **Why these engines** (#565, the spike on AMI-ci on the Mac): Kyutai STT 1B was the only candidate under 1 s for committed words (p95 0.89 s), since it is streaming by design: a fixed 0.5 s delay, a text token every 80 ms, and no revisions. Apple's recognizer was the most accurate (WER 14.8 %), but commits words only at phrase ends (p95 6.1 s). The Owner chose both, with Kyutai the default. The pyannote 3.1 model card reports a DER of 18.8 % on AMI headset-mix, scored without a collar and with overlap included. That is the same scoring as Q1, and inside its 25 %.
- **CI uses the default models,** so that CI's subset checks (G1-8c) test what the Mac measures. The model files go into CI's cache, keyed by the model manifest's hash, so they are downloaded once and not on every run.
- **Options considered (#81, questions 7 and 8; the ASR one superseded by G4, #565):**
  - **ASR:** faster-whisper was *recommended*: one engine for Linux CI and the Mac, CPU int8, deterministic, with word timestamps and VAD built in. mlx-whisper is fast on Apple GPUs but doesn't run on Linux, so CI would test a different engine. whisper.cpp (`pywhispercpp`) has Metal on the Mac and CPU on Linux, but its Python binding is less mature. Either alternative could become a later Mac-only speed backend, if Q2 needs one.
  - **Diarization:** `speaker-diarization-3.1` on pyannote.audio 3.x is *recommended*: it meets Q1 by its own model card. `speaker-diarization-community-1` on pyannote.audio 4.x is reported to be more accurate, but 4.x's telemetry would need checking against Q8, and switching costs time before the deadline. Both carry CC BY 4.0, 3.1 through its embedding model, which the Owner accepted with attribution (#81, answer 13a). sherpa-onnx (Apache-2.0) needs no token, but its DER on AMI is unmeasured.

**Model handling (`models`).** The model manifest (`src/lmt/models.toml`) lists each model's repository, revision (a commit hash) and every file with its SHA-256 and size. It also records each model's licence and attribution, as its model card gives them: the creators, the licence and a link to the card. `NOTICE` and the README's `## Licences` section give that attribution for every model in the manifest (§7, #81 answer 13a), and a test keeps both in step with it (spec, G1-15). `lmt models download` fetches exactly those files with `huggingface_hub`, verifies each one, and deletes any file that doesn't match (exit 5, Q9). The cache is `LMT_CACHE_DIR` (default `~/.cache/lmt/models`). Once every file there is verified, the product sets `HF_HUB_OFFLINE=1` before importing any model library, so nothing tries the network (Q8, L4). `lmt transcribe` downloads missing models on first use, saying so on stderr. `--offline` forbids that.

**Determinism (Q7).** Models are pinned by hash, Kyutai decodes greedily at temperature 0 with the same quantization at every load, and torch's thread count is fixed. Torch also runs with `torch.use_deterministic_algorithms(True)`, and pyannote's clustering is seeded. The spike's three Kyutai runs gave identical text (#565). `lmt eval` compares two runs (G1-5, G1-12). Apple's engine is exempt: macOS manages its model, so its figures carry the macOS version and build instead (G4-6).

## Speech engines (G4)

Each choice here is the recommended option on #570, waiting for the Owner's approval. What it is judged by is in the spec, G4.

**The interface** (`engines/`). Both engines take what decode gives (16 kHz mono float32) and give words, so the pipeline, alignment, the join, export and the harness don't know which engine ran.

```
engines.load(name, *, offline) -> Engine                  # "kyutai" | "apple"; exit 5 if it can't run here
Engine.info -> dict                                        # the transcript's models.asr entry, with "engine"
Engine.transcribe(audio) -> list[Word]                     # batch: the whole recording
Engine.stream() -> Stream                                  # live: one per session
Stream.feed(block) -> list[Piece]                          # committed pieces, in order, at most once each
Stream.finish() -> list[Piece]                             # the rest, once the source has stopped
Piece(text, start, end, starts_word, probability)          # times in seconds from the start of the audio
```

`engines.words(pieces)` joins pieces into `Word`s by G4's rules (spec, G4 "Terms"), and also says which word is complete, so batch and live mode build words the same way. For Apple's engine a piece is a whole word, so each one starts a word. A `Word`'s probability is the lowest of its pieces' (Kyutai's token probability at temperature 0; Apple's `transcriptionConfidence`).

**Kyutai** (`engines/kyutai.py`). One streaming loop serves both modes. Audio is resampled from 16 to 24 kHz (decode's resampler), then each 1,920-sample (80 ms) frame goes through Mimi's `encode_step` and the language model's `step` (`moshi_mlx.models.LmGen`, temperature 0), which gives at most one text token. The stream starts with the model's silence prefix (`stt_config`), and at the end it is padded with its `audio_delay_seconds` (0.5 s) plus 1 s of silence, so the last words come out. A token's time is its step's time minus the 0.5 s delay.
- **Batch** runs the loop over the whole recording as fast as the GPU goes, with no pacing. The spike measured 0.44 of real time on the Mac, so Q2's 0.5 holds if diarization keeps up beside it.
- **Live** runs the same loop in the ASR worker: `feed` takes the source's 0.1 s blocks, runs every whole frame they complete, and returns the pieces those frames gave. Kyutai never revises a token, so every piece is committed as it comes, with no LocalAgreement and no buffer to re-decode.
- **No speech:** a recording for which Kyutai gives no word is "no speech found" (exit 4), as before. Kyutai gives padding, not text, in silence, so no VAD is needed.
- **Memory** stays bounded: `LmGen` keeps a fixed-size attention cache, so an hour costs what a minute does, besides the transcript.

**Apple's engine** (`engines/apple.py`, with the helper's source in `src/lmt/helper/lmt-speech/`).
- **The helper** is one Swift file and a `Package.swift`, built from source in this repository (§7). It calls `SpeechAnalyzer` with a `SpeechTranscriber` for `en-US`, with `reportingOptions [.volatileResults, .fastResults]` and `attributeOptions [.audioTimeRange, .transcriptionConfidence]`. It converts the samples to the analyzer's preferred format with `AVAudioConverter`.
- **How it's built.** The first time Apple's engine is used, or by `lmt models download --engine apple`, `lmt` runs `swiftc -O` from the Mac's Command Line Tools on the source shipped in the package, into `LMT_CACHE_DIR/helper/<the source's SHA-256>/lmt-speech`. A change to the source changes the directory, so a stale binary is never run, and nothing is written outside the cache (Q8). No binary is downloaded or committed. Without `swiftc`, Apple's engine exits 5, naming `xcode-select --install` (G4-2). Kyutai's users need no Swift. *Options:* building at install time would make every install need the Command Line Tools, Kyutai's users' included, and a prebuilt binary isn't "built from source in this repository" (#570, question 3).
- **How it's called.** `lmt` starts it as a subprocess, with no shell, an argument list fixed by `lmt`, and no path from the user: `lmt-speech status`, `lmt-speech install` or `lmt-speech transcribe`, each with `--locale en-US`. For `transcribe`, `lmt` writes the samples to its stdin as raw 16 kHz mono float32, little-endian: the whole recording in batch mode, then end of file; each block as it arrives in live mode. So the helper never opens the user's file, and decode stays the only parser of untrusted bytes (Q4, Q9).
- **Its protocol** is one JSON object per line on stdout; stderr is for diagnostics, which `lmt` shows only with `--verbose`.
  - `status` and `install` print `{"type": "status", "os": "26.6.2", "build": "25G…", "locale": "en_US", "supported": true, "installed": true}`, then exit 0. `install` first calls `AssetInventory.reserve(locale:)`, then `assetInstallationRequest`, so macOS downloads the assets. Only `lmt models download --engine apple` runs `install` (G4-7).
  - `transcribe` prints that status line first, then `{"type": "volatile", "start": s, "end": s, "text": "…"}` for provisional text, `{"type": "final", "start": s, "end": s, "words": [{"text": "…", "start": s, "end": s, "confidence": c}]}` for each final result, and `{"type": "done"}` once its input has ended and every result is out, then exits 0. Times are seconds from the start of the input. The words and their times come from the final result's `audioTimeRange` runs.
  - A failure prints `{"type": "error", "code": "unsupported" | "not-installed" | "denied" | "failed", "message": "…"}` and exits 3. `lmt` turns the first three into exit 5 with G4-2's line, and `failed` into an internal error (exit 1).
- **Volatile results** are shown on a terminal in live mode, as provisional text, and never committed or written (spec, G4 "Terms"). Only final results' words become pieces.
- **In CI** the helper is built and its `status` is run on `macos-26`, where it reports `unsupported` (A5), which is G4-2's real case. The Python side is tested against helper output recorded on the Mac and committed as fixtures. Apple's model tests and figures run on the Mac (A5).

**Errors.** `engines.load` checks that the engine can run before any audio is captured or output written: for Kyutai, that its files are verified (exit 5 with `--offline`, as before); for Apple's, macOS 26 or later, the helper built, and `status` saying supported and installed.

**Options considered (#570):**
- **The engine choice:** *A, recommended:* one `--engine` option on `transcribe` and `live`, replacing `--model`, since each engine has one model. *B:* keep `--model` with model names from both engines; but Apple's engine has no model name the user can pick, and two options would overlap.
- **Kyutai in batch mode:** *A, recommended:* the streaming loop, unpaced, so batch and live give the same words for the same audio. *B:* a batched offline pass, which the model isn't trained for and `moshi-mlx` doesn't offer.
- **Apple's engine from Python:** *A, recommended:* the Swift helper over pipes, which the Owner allowed (§7). *B:* PyObjC bindings to the Speech framework; but `SpeechAnalyzer` is a Swift-only, `async` API that PyObjC can't call.

## Evaluation harness (`lmt.eval`)

- **Dataset manifests** (`src/lmt/eval/manifests/*.toml`) list every file of LS full, AMI full and the CI subset, with its URL and SHA-256. They also give the recipes for the one-hour recording, the reference clip and the two-speaker clip. Sources: LibriSpeech test-clean from openslr.org; AMI Mix-Headset audio and manual annotations v1.6.2 from the AMI corpus site; and the `only_words` RTTMs from `BUTSpeechFIT/AMI-diarization-setup` at a pinned commit. All are CC BY 4.0. Downloads go to `LMT_DATA_DIR` (default `~/.cache/lmt/data`) and are verified by checksum.
- **Scoring:** WER with `jiwer` (Apache-2.0), after Whisper's `EnglishTextNormalizer`. The normalizer is vendored at a pinned openai-whisper commit, with its MIT notice and its `english.json`, which avoids depending on openai-whisper itself. DER with `pyannote.metrics` (MIT). Both follow the spec's "Terms".
- **Systems:** the product run; the engine alone (`asr-alone`: the ASR stage's words, scored for WER); and pyannote alone (the diarization stage's turns, scored for DER). Each stage's output is computed once per file and reused.
- **Engines (G4):** `lmt eval --engine apple` runs every system with Apple's engine and writes `results/<set>-apple.json`, with Apple's version record. Without it, Kyutai, into `results/<set>.json`. With Apple's engine, the harness also records the helper's peak memory (G4-5) and skips the repeat comparison (G4-6).
- **Output:** `results/<set>.json`, and the README table rendered from every results file present: `full`, `full-apple`, `live` and `live-apple` (format in `public-api.md`).
- **Eval-only dependencies** are an extra, `lmt[eval]`, so a user's install doesn't carry them.

## Live mode (G2)

G2 reuses decode, the ASR engine, the diarization models, alignment's rules, export and the transcript types. It adds an audio source and streaming forms of ASR and diarization, behind the same plain-data interfaces (audio arrays, lists of words and turns, never files). What it is judged by is in the spec, G2. Each choice below is the recommended option on #82, waiting for the Owner's approval.

```
microphone (sounddevice) ─┐
                          ├─► blocks (16 kHz mono float32) ─┬─► streaming ASR ──────────► committed words
file (--from-file, paced) ┘                                 └─► incremental diarization ─► final speaker activity
                                                                                              │
                                        committed words + speaker activity ─► join ─► events (stdout), <stem>.txt
                                                                                  └─► at stop: txt, srt, vtt, json
```

- **Sources** (`live/source.py`). The **microphone source** opens the chosen input device with `sounddevice` (PortAudio) at the device's own rate and channels, and resamples to 16 kHz mono with decode's resampler. The device's callback only copies blocks into a queue, so a slow stage never makes it drop audio. The **file source** decodes with `audio.decode`, then hands over 0.1 s blocks at real-time pace. Its **lockstep** mode, for tests, waits for both streaming stages before each block (spec, G2 "Terms"). If a device gives exact zeros for its first 3 s, stderr warns that the microphone may be blocked, naming macOS's setting, and capture goes on. macOS gives a denied app silence rather than an error, but a loopback device such as BlackHole also gives exact zeros while nothing plays, as at the start of a call, so silence alone can't be an error. The check is only for a device, and only for its first 3 s.
- **Streaming ASR** (`live/asr.py`, G4). The ASR worker feeds each block to the chosen engine's `Stream` ("Speech engines (G4)") and passes on the pieces it returns, each committed as it comes. With Kyutai, a piece comes 0.5 s after its audio, plus up to one block. With Apple's engine, pieces are the words of each final result, so they come at phrase ends. G2's LocalAgreement-2 over a re-decoded buffer, and the VAD that cut it, are gone with Whisper (#565).
- **Incremental diarization** (`live/diarize.py`). This is the online method of Coria et al. (2021), "Overlap-aware low-latency online speaker diarization based on end-to-end local segmentation", on the same pinned models as G1. Every step (0.5 s), `segmentation-3.0` runs on the latest 5 s window, giving up to three local speakers. Each local speaker active long enough gets a `wespeaker` embedding from its frames. Local speakers are matched to the speakers found so far by cosine distance, two local speakers never taking the same one. A local speaker farther than a threshold from every centroid becomes a new speaker, up to `--max-speakers`. Centroids are updated as each speaker is matched. Speaker activity is final once a frame is a fixed latency old (1.0 s, provisional), and it never changes after that. The thresholds and latency are tuned on AMI's dev meetings, never on its test meetings, and the internal design records them. It is implemented here, on pyannote.audio's model API, rather than taken from the `diart` package (below).
- **Words before labels** (`live/join.py`, G4; #565). Each committed piece goes out at once as a `text` event, before any label, so the reader sees the words as they're said. The join joins pieces into words (`engines.words`). A word is labelled once it is complete and speaker activity is final up to its end, by alignment's rules (G1, "Pipeline"), and segments break by the same rules. Each labelled word then goes out as a `words` event, and a `segment` event closes its segment, as in G2. So a word's delay is its piece's (Kyutai's 0.5 s, plus the compute time), and its label's delay is the later of its completion and the diarization latency, plus the compute time. The `words` and `segment` events, and everything written at the stop, are unchanged, so a reader of live events 1.0 still works.
- **Delay budget** (G2-6c, Q10). Both stream delays (spec, G2 and G4 "Terms") are measured from a word's end. *Words:* a word's last piece comes 0.5 s after its audio ends (Kyutai's fixed delay; the word's end is its last step's end), and is handed over at the next 0.1 s block boundary, so the stream delay is 0.5 to 0.6 s, under G2-6c's 0.7 s. Q10's 1.0 s then leaves at least 0.4 s for the compute from a block's arrival to its event, where the spike measured 35 ms a step at p50 (#565). *Labels:* activity is final at the first step at which it is the latency L old, so at most L + S, where S is the step; and the word must be complete, which takes at most 0.24 s more than its last piece, or until the next word's first piece. At L = 1.0 s and S = 0.5 s, that is 1.5 s, under G2-6c's 2.0 s; the spike measured labels at p95 1.55 s on the Mac with compute (#565), against Q10's 3.0 s.
- **Threads.** The device callback, the ASR worker and the diarization worker each run in a thread of their own; with Apple's engine, a reader thread also takes the helper's stdout. The join and the writers run in the main thread. A worker that falls behind takes in all the new audio at its next update, so it catches up rather than drifting, and never skips audio. If the pipeline is more than 5 s behind real time, stderr says so.
- **Stopping.** Ctrl-C (SIGINT), SIGTERM, `--duration` and the end of a `--from-file` input all stop the source at once. The workers then finish the audio already captured: ASR commits what's left in its buffer, and diarization makes the rest final. Then the join labels the remaining words and the outputs are written. A second Ctrl-C during that abandons the save (exit 130).
- **What's written** (#82, question 5). Segments are printed to stdout as they're recognised: as text lines, or as JSON events with `--jsonl`. If `txt` is among the formats, `<stem>.txt` gets each segment as it completes, flushed, so a crash keeps what was said. At the stop, every requested format is written from the same transcript as the live stream, `txt` included, so what's saved is what was shown. With `--save-audio`, `<stem>.wav` is written as the audio arrives (16 kHz mono, 16-bit PCM, about 115 MB an hour), so `lmt transcribe` can redo the session at offline quality afterwards. Nothing else is written (Q8).
- **Memory** stays bounded however long the meeting: Kyutai's attention cache is fixed in size, the diarization window is 5 s, and there is one centroid per speaker. Only the transcript grows.
- **The live model** (G4, #565). Live mode uses the same engine and model as batch mode, chosen by `--engine`. The diarization latency stays 1.0 s: the spike measured labels at p95 1.55 s with it, and 2.0 s at 1.5 s, both within Q10's 3.0 s, at a DER of 19.7 % and 19.6 % on AMI-ci. If G2-6's label delay fails on the Mac, 0.5 s is the first remedy; if DER needs more context, 1.5 s still meets Q10.

**Options considered (#82):**
- **The command (question 6).** *A, recommended:* a subcommand, `lmt live`, that runs in the foreground until Ctrl-C, `--duration` or the end of `--from-file`. *B:* `lmt transcribe --live`, which mixes two option sets that mostly don't apply to each other. *C:* `lmt live start` and `lmt live stop`, with a background process: more to get wrong (a stray process holding the microphone, its state on disk), for no gain over a terminal window.
- **Streaming ASR (question 3; superseded by G4, #565, which took option C with Kyutai STT 1B).** *A, recommended then:* LocalAgreement-2 over a rolling buffer, with the same engine as G1. *B:* cut the audio at pauses found by the VAD, and transcribe each piece once. That is simpler, but a word at the start of a 10 s turn waits about 10 s, which fails Q10 in meetings, where turns are long. *C:* a streaming-native engine, such as sherpa-onnx's streaming Zipformer (Apache-2.0). Its delay is low, but it is a second ASR engine, with a second model to pin and its accuracy on AMI unmeasured.
- **Incremental diarization (question 4).** *A, recommended:* the online method above, implemented here on the pinned pyannote models. *B:* the `diart` package (MIT), which implements that method. It brings its own dependency tree and pins of pyannote.audio, and gives less control over determinism and threads. *C:* re-run G1's offline diarization on everything so far, every few seconds. It is accurate, but its cost grows with the meeting's length, and labels already shown could change.
- **What's saved at the stop (question 5).** *A, recommended:* exactly what was shown live, with `--save-audio` for an offline-quality pass afterwards. *B:* re-run offline diarization on the whole session at the stop, so the saved file gets G1's speaker accuracy. That costs minutes at the end of an hour's meeting, and the saved labels could differ from those shown.
- **Capture.** *Recommended:* `sounddevice` (MIT). Its macOS wheel bundles PortAudio (MIT); on Linux it uses the system's `libportaudio2`, which is imported only when a device is opened, so CI and `lmt transcribe` never need it. The alternatives: PyAV's `avfoundation` input, which depends on PyAV's wheel being built with FFmpeg's device library, and is macOS-only; or PyAudio (MIT), whose macOS install needs PortAudio from Homebrew.
- **Audio from the call itself (question 2).** On a call, the microphone picks up only the room, so remote speakers are captured only through the computer's speakers. *Recommended:* G2 records from the microphone or from any input device the user picks with `--device`. So a loopback device the user has installed works, but none is bundled: BlackHole, the common one, is GPL-3.0. Capturing system audio directly (ScreenCaptureKit, or macOS 14.4's audio taps) would be a later goal.

## Speaker names (G3, F7)

- **`rename`** (`rename.py`) reads a transcript JSON, validates it against the schema, replaces labels, and hands the transcript to `export`. It never re-runs a model, so it takes well under a second.
- **One rendering path.** Times are rounded to the millisecond once, when alignment builds the transcript. Every exporter renders from those rounded values, and the JSON stores them. So a transcript read back from its JSON renders byte-identical files (G3-1), and `rename` can't drift from `transcribe`.
- **Escaping lives in the exporters,** so each format's rules are in one place. WebVTT escapes `&`, `<` and `>` in cue text, escapes `&` in the voice tag's annotation, and puts the label both in the voice tag and as visible text. SRT needs no escaping, because names can't hold `<`, `>`, `{` or `}`, the characters some players read as markup.
- **Options considered (#83, question 5):**
  - **A. `lmt rename TRANSCRIPT S1=Alice …`,** which rewrites the JSON and re-exports in place. *Recommended:* it is U4 in one command, and with no names it lists the speakers, so you can tell who is who.
  - **B. `lmt export TRANSCRIPT --name S1=Alice`,** a general re-export command. It is more general, but two steps' worth of options for one task, and nothing else needs a re-export yet.
  - **C. Renaming in the demo page,** saved back to the files. That needs the server to write files, which the demo otherwise never does (Q8). It could come later, through the same `rename` code.

## Demo (G3, F8)

```
lmt demo ─► decode (audio.py), once ─► 16 kHz mono WAV, in memory
        └─► transcript JSON, validated at start
             └─► local HTTP server (127.0.0.1, random token) ─► page: transcript list + <audio> + <track>
                  on each request for the transcript or the track:
                  read the JSON again ─► validate ─► the JSON, or the WebVTT exporter's rendering, in memory
```

- **Server** (`demo/server.py`): Python's standard `http.server.ThreadingHTTPServer`, bound to `127.0.0.1`, on the given port or one the system picks. Every route sits under a random 128-bit token from `secrets`. A request without it gets 404, and one whose `Host` header isn't `127.0.0.1:<port>` or `localhost:<port>` gets 403. That stops other web pages reaching it through DNS rebinding. Only GET and HEAD are served. Responses carry `Content-Security-Policy: default-src 'self'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
- **Audio:** decode turns the recording into 16 kHz mono, which is served as 16-bit PCM WAV from memory, with byte ranges. Every browser plays WAV, whatever the input format (MOV and FLAC differ between browsers), and seeking in PCM is exact, where seeking in a variable-bit-rate MP3 isn't. Two hours come to about 230 MB of memory, within Q3. Nothing is written to disk (Q8). The cost is speech-band sound, which is enough to check a transcript.
- **Page** (`demo/static/`): one HTML file, one script and one stylesheet, plain JavaScript with no build step and no third-party code, shipped in the wheel. It fetches the transcript JSON and builds the list. Each segment is a `button` with its time, label and text, so the keyboard reaches it. Clicking sets the audio's `currentTime` to the segment's `start` and plays. As the audio plays, the current segment is marked `aria-current="true"` and scrolled into view. The speakers are listed with their labels and speaking time. All text goes in through `textContent`, never `innerHTML`, so a transcript can't inject markup (Q9). The page also loads the WebVTT as a `<track>`, which the browser test uses to check Chrome's parse (G3-2).
- **The transcript stays live.** The server reads the transcript JSON from disk again, and validates it against the schema, on every request for it and for the track. The track is rendered in memory by the WebVTT exporter (`export/vtt.py`) from that same transcript, never read from a `.vtt` file. So the demo writes nothing, works with `-f json`, and after `lmt rename` a reload shows the new labels in the list and the track alike. `rename` renames its files into place, so a read sees either the old file or the new one. A file that has become invalid gets 500 on both routes, one `lmt: warning: <file>: <problem>` line on stderr, and an error message on the page; the server keeps running, so fixing the file and reloading recovers. Only the audio is decoded once, at start.
- **`--sample`** fetches the sample meeting through the dataset manifest's cache in `LMT_DATA_DIR`. It transcribes it once with the default models, and keeps the transcript there, keyed by the audio's SHA-256 and the model revisions. A later run with the same models serves the cached transcript, with no model loaded. It runs on the plain install, without the `eval` extra: of `lmt.eval`, it uses only `datasets.py` and the manifests, which import nothing from the extra. Of `lmt`'s modules, only `eval/score.py` imports `jiwer` and `pyannote.metrics` (see "CI" for the test). The plain install has no `jiwer`; it does have `pyannote.metrics`, which `pyannote.audio` 3.4 depends on.
- **Options considered (#83, question 8):**
  - **A. The standard library's HTTP server and a plain page** (above). *Recommended:* no new dependency, nothing to lock or vet, works offline, and small enough to review whole.
  - **B. Gradio or Streamlit.** Quick to build, but each brings a large dependency tree, and both collect usage statistics unless turned off, against Q8.
  - **C. FastAPI and uvicorn.** Two dependencies for what the standard library already does here.
  - **D. A single HTML file, written beside the transcript, with no server.** F8 asks for a served page. A file opened from disk can't fetch the JSON in Chrome, and embedding the audio makes a large file, which is a write Q8 doesn't expect.
- **The browser test** uses Selenium WebDriver (Apache-2.0, in the `dev` dependency group) to drive headless Chrome, with the Chrome and `chromedriver` preinstalled on the `ubuntu-24.04` image. So no browser is downloaded or locked. Its dependencies (`urllib3`, `trio`, `websocket-client`, `certifi` and the like) fall in the licence classes the Owner accepted (§7), and the item that adds it posts the inventory. Playwright was the alternative. It downloads its own Chromium and bundles Node.js, whose licences go beyond §7's list. The same script takes `docs/demo.png` (G3-9), in Chrome at a fixed window size, on the sample meeting.
